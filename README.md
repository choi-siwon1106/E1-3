# Mini NPU Simulator

입력 패턴과 필터(Cross / X)를 **위치별로 곱하고 모두 더하는 MAC(Multiply-Accumulate) 연산**으로
패턴이 십자가인지 X인지 판정하고, 크기별 연산 시간을 측정하는 Python 콘솔 프로그램입니다.

- 언어: Python 3.8 이상 (Python 3.10.5에서 동작 확인)
- 외부 라이브러리 없음 (`json`, `math`, `os`, `re`, `sys`, `time`, `unicodedata`만 사용)

```
2. data.json 분석
3. 패턴 생성기 (보너스)
선택:
```

| 모드 | 설명 |
|---|---|
| `1` | 3×3 필터 A, B와 패턴을 한 줄씩(공백 구분) 입력하면 점수·연산 시간·판정(A / B / 판정 불가)과 3×3 성능을 출력 |



## 2. 구현 요약

### 2-1. 데이터 구조
- n×n 배열은 **리스트의 리스트**(`list[list[float]]`)로 저장합니다.
- `create_matrix(n)`, `get_value(m, r, c)`, `set_value(m, r, c, v)`로 생성하고, 특정 위치의 값을 읽고 씁니다.
- `validate_matrix()`는 정사각형인지, 모든 값이 숫자인지, 기대 크기와 같은지를 검사합니다. 크기에 제한이 없어 3×3, 5×5, 13×13, 25×25를 모두 처리합니다.

### 2-2. 라벨 정규화
`data.json`은 같은 의미의 라벨을 여러 표기로 씁니다.

| 위치 | 원본 표기 | 표준 라벨 |
|---|---|---|
| `patterns.*.expected` | `"+"` | `Cross` |
| `patterns.*.expected` | `"x"` | `X` |
| `filters.size_N` 키 | `"cross"` | `Cross` |
| `filters.size_N` 키 | `"x"` | `X` |

`normalize_label()`은 공백을 제거하고 소문자로 바꾼 뒤 별칭 표(`LABEL_ALIASES`)에서 찾습니다.
필터 키와 expected 값 **모두 같은 함수**를 거치므로, 판정 결과(`Cross`/`X`)와 expected를 항상 같은 기준으로 비교합니다.
해석할 수 없는 라벨(예: `"circle"`)은 `None`이 되고, 해당 케이스는 "라벨 오류"로 FAIL 처리됩니다.

### 2-3. MAC 연산
```python
def mac(pattern, filt):
    n = len(pattern)
    total = 0.0
    for r in range(n):
        for c in range(n):
            total += pattern[r][c] * filt[r][c]
    return total
```
NumPy 없이 이중 반복문으로 같은 위치끼리 곱해 누적합니다. N×N 배열이면 곱셈과 덧셈을 각각 **N²번** 합니다.

### 2-4. 동점 처리 정책 (epsilon)
```python
EPSILON = 1e-9
if abs(score_a - score_b) < EPSILON:
    return UNDECIDED
```
두 점수 차이가 `1e-9`보다 작으면 부동소수점 오차 범위의 **동점**으로 보고 `UNDECIDED`(모드 1에서는 "판정 불가")를 반환합니다.
동점이 아니면 점수가 큰 쪽 라벨을 반환합니다. `UNDECIDED`는 expected(`Cross`/`X`)와 같을 수 없으므로 항상 FAIL입니다.

### 2-5. data.json 검증 흐름 (모드 2)
각 패턴은 아래 순서로 검사하며, 어느 단계에서 실패해도 **그 케이스만 FAIL**로 기록하고 다음 케이스로 넘어갑니다. 프로그램은 중단되지 않습니다.

1. 키 형식 `size_{N}_{idx}` 확인 → 정규식으로 N 추출
2. `size_N` 필터가 로드되어 있는지 확인
3. `input` 항목이 있는지 확인
4. `input`이 N×N 숫자 배열인지 확인 (행/열 수, 숫자 여부, 필터 크기와 일치 여부)
5. Cross / X 필터와 각각 MAC 연산
6. epsilon 규칙으로 판정
7. expected 라벨을 정규화해 판정과 비교 → PASS / FAIL

`data.json` 파일이 없거나 JSON 문법이 틀린 경우에도 안내 메시지를 출력하고 정상 종료합니다.

### 2-6. 성능 측정
- `time.perf_counter()`로 **MAC 함수 호출 구간만** 측정합니다. 입력, 출력, 파일 읽기, 1차원 변환은 측정에서 제외합니다.
- 첫 호출 1회는 워밍업으로 버리고, 이어서 **10회 반복 측정한 평균**을 ms 단위로 출력합니다.
- `data.json`에는 3×3 필터가 없으므로 3×3은 패턴 생성기로 만든 십자가 패턴/필터로 측정합니다.
  5×5, 13×13, 25×25는 `data.json`의 Cross 필터와 생성기로 만든 같은 크기의 십자가 패턴으로 측정합니다.

### 2-7. 보너스
- **패턴 생성기**: `generate_cross(n)`, `generate_x(n)`으로 임의 크기의 십자가/X 패턴을 만듭니다. 생성한 패턴은 세 곳에서 재사용합니다.
  - **모드 3**: 크기 N을 입력받아 두 패턴을 생성하고 출력합니다. 생성한 패턴을 필터로도 써서 Cross 패턴은 Cross로, X 패턴은 X로 판정되는지 PASS/FAIL로 검증합니다. 그 크기의 2D/1D 성능도 측정합니다.
    예를 들어 5×5에서는 Cross 패턴의 점수가 Cross 9.0, X 1.0으로 Cross로 판정됩니다.
  - **모드 1**: 첫 줄에 `cross` / `x`를 입력하면 생성기 패턴으로 필터나 패턴을 채웁니다.
  - **성능 분석**: `data.json`에 없는 3×3 측정용 패턴/필터와, 각 크기의 측정용 입력 패턴을 생성기로 만듭니다.
  - 짝수 N은 정중앙 칸이 없어 십자가가 한 칸 치우칩니다. 모드 3은 이때 안내 문구를 출력합니다. 그래도 Cross와 X는 정상적으로 구분됩니다.
- **1차원 배열 최적화**: `flatten()`으로 길이 N²의 1차원 리스트로 바꾼 뒤 `mac_flat()`으로 단일 반복문 연산을 합니다.
  같은 입력, 같은 반복 횟수로 2D 버전과 시간을 비교한 표를 함께 출력합니다.

### 3-2. 실패 원인 분석

실패 원인은 **데이터/스키마 문제, 로직 문제, 수치 비교 문제** 세 가지로 나눠 점검했습니다.

**① 데이터/스키마 문제: 해당 없음 (라벨 정규화로 예방)**
- 6개 패턴 모두 키 형식(`size_N_idx`)이 올바르고, `input`이 N×N이며 필터 크기와 일치합니다.
- expected가 `"x"`, `"+"`로, 필터 키가 `"cross"`, `"x"`로 표기가 서로 다릅니다.
  정규화 없이 `"x" == "X"`나 `"+" == "Cross"`처럼 비교했다면, 점수와 판정이 맞아도 PASS여야 할 케이스까지 FAIL이 되었을 것입니다.
  `normalize_label()`로 양쪽을 `Cross`/`X`로 통일해 이 유형의 실패를 0건으로 만들었습니다.

**② 로직 문제: 해당 없음**
- PASS 3건(size_5_2, size_13_1, size_25_2)은 점수 차이가 8.8 이상으로 크고, 판정이 expected와 일치합니다.
  MAC 연산과 필터 선택(키에서 N 추출 → `size_N`)이 올바르게 동작한다는 근거입니다.

**③ 수치 비교 문제: 실패 3건의 원인**
- 실패 3건은 모두 **두 점수가 수학적으로 정확히 같은 값**이 되도록 설계된 케이스입니다.
  - size_5_1 (X 입력): Cross 필터와는 중앙 1칸만 겹쳐 `1 × 0.9 = 0.9`, X 필터와는 9칸이 겹쳐 `9 × 0.1 = 0.9`
  - size_13_2 (십자가 입력): Cross 필터 25칸 × 0.3 = `7.5`, X 필터는 중앙 1칸 × 7.5 = `7.5`
  - size_25_1 (X 입력): Cross 필터 중앙 1칸 × 4.9 = `4.9`, X 필터 49칸 × 0.1 = `4.9`
- 그런데 `0.1`, `0.3` 같은 값은 2진 부동소수점으로 정확히 표현되지 않아, 여러 번 더하면 오차가 쌓입니다.
  그 결과 `0.8999999999999999`, `7.499999999999997`처럼 **1e-16 ~ 1e-15 수준의 차이**가 생깁니다.
- 단순히 `>`로 비교하면 이 오차 때문에 한쪽이 이긴 것처럼 보이고, 판정이 오차의 방향에 따라 우연히 정해집니다.
  예를 들어 size_5_1은 0.9 > 0.8999…라서 Cross로 판정되어 근거 없는 오답이 됩니다.
- 그래서 `|Cross − X| < 1e-9`이면 동점으로 보는 epsilon 정책을 적용했습니다. 세 케이스의 차이(최대 2.66e-15)는 epsilon보다 6자릿수 이상 작으므로 `UNDECIDED`로 판정됩니다.
  `UNDECIDED`는 expected와 같을 수 없으므로 **동점 규칙에 따라 FAIL**입니다.
- 즉 이 3건의 FAIL은 버그가 아니라, **필터가 두 패턴을 구분하지 못한다는 사실을 정책대로 정확히 보고한 결과**입니다.
  PASS로 만들려면 비교 정책을 바꿀 것이 아니라, 중앙 가중치(0.9, 7.5, 4.9)를 조정해 두 필터의 점수가 갈리도록 **필터 자체를 개선**해야 합니다.

### 3-3. 성능 분석과 시간 복잡도

측정 환경: Windows 11, Python 3.10.5. 값은 실행마다 조금씩 달라집니다. 이 절과 3-4절의 표는 **같은 1회 실행**에서 나온 결과입니다.

| 크기 | 평균 시간(ms, 10회) | 연산 횟수(N²) | 연산당 시간(ns) |
|---|---|---|---|
| 3×3 | 0.00097 | 9 | 107.8 |
| 5×5 | 0.00187 | 25 | 74.8 |
| 13×13 | 0.01004 | 169 | 59.4 |
| 25×25 | 0.03878 | 625 | 62.1 |

**O(N²) 근거**
- `mac()`은 바깥 반복 N번 × 안쪽 반복 N번으로, 곱셈과 덧셈을 정확히 **N²번** 합니다. 그 외 작업은 상수 시간입니다.
  따라서 시간 복잡도는 **O(N²)**이고, 입력 배열의 원소 수에 정비례합니다.
- 측정값도 이를 따릅니다. 13×13 → 25×25에서 연산 횟수는 625 / 169 = **3.70배**, 측정 시간은 0.03878 / 0.01004 = **3.86배**로 거의 같은 비율로 늘었습니다.
- 5×5 → 25×25에서 연산 횟수는 25배, 시간은 약 20.7배입니다. 차이가 나는 이유는 작은 크기에서 함수 호출, `range` 생성, 타이머 호출 같은 **고정 비용**의 비중이 크기 때문입니다.
- 그래서 연산당 시간이 3×3에서 약 108ns로 가장 크고, N이 커질수록 약 60ns로 **일정한 값에 수렴**합니다.
  연산당 비용이 상수에 수렴한다는 것은 전체 시간이 연산 횟수 N²에 비례한다는 뜻이므로, O(N²)의 실측 근거가 됩니다.
- 이 추세대로라면 N이 2배가 되면 시간은 약 4배, N이 10배가 되면 약 100배가 됩니다.
  실제 AI 모델처럼 수백×수백 크기 필터를 수천 개 쓰면 직렬 반복문으로는 감당하기 어렵고, 수천 개의 MAC을 동시에 처리하는 NPU가 필요한 이유가 여기에 있습니다.

**측정 시 주의점**
- 3×3 연산은 1µs 남짓이라 타이머 해상도와 OS 스케줄링의 영향을 크게 받습니다. 실행마다 값이 수십 % 흔들릴 수 있으므로, 절대값보다 **크기 간 비율**로 해석했습니다.
- 10회 평균은 과제의 최소 기준입니다. 더 안정적인 값이 필요하면 `REPEAT`를 늘리면 됩니다.

### 3-4. [보너스] 2D vs 1D 배열 비교

| 크기 | 2D(ms) | 1D(ms) | 1D/2D |
|---|---|---|---|
| 3×3 | 0.00097 | 0.00056 | 0.58 |
| 5×5 | 0.00187 | 0.00112 | 0.60 |
| 13×13 | 0.01004 | 0.00643 | 0.64 |
| 25×25 | 0.03878 | 0.03966 | 1.02 |

- 3×3 ~ 13×13에서는 1D가 약 **36~42% 빨랐습니다**. 반복문이 하나라 안쪽 `range` 생성이 N번에서 1번으로 줄고, `a[r][c]`의 2단계 인덱싱이 `a[i]` 1단계로 줄었기 때문으로 봅니다.
- 반면 25×25에서는 1D가 **빠르지 않았습니다**. 여러 번 실행해도 비율이 1.0 안팎(1.02~1.17)으로 나와, 일시적인 측정 잡음으로 보기는 어렵습니다.
  N이 커질수록 반복 오버헤드보다 곱셈·덧셈 자체의 비용이 커져 줄일 수 있는 부분의 비중이 작아진 것으로 추정하지만, 원인은 직접 확인하지 못했습니다.
- 어떤 방식이든 연산 횟수는 똑같이 N²이므로 **시간 복잡도는 O(N²)로 같고**, 줄어드는 것은 상수 계수뿐입니다.

### 3-5. 정리
- 6건 중 3건 PASS, 3건 FAIL이며, FAIL 3건은 모두 **수학적 동점 + 부동소수점 오차**를 epsilon 정책으로 동점 처리한 결과입니다.
- 라벨 정규화 덕분에 표기 차이(`+`/`cross`/`x`)로 인한 실패는 0건이고, MAC/필터 선택 로직 오류도 0건입니다.
- 연산 시간은 N²에 비례해 증가하며, 연산당 시간이 상수에 수렴하는 것으로 O(N²)를 확인했습니다.
